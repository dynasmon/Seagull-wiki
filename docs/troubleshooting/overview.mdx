description: 'Find the failing boundary before changing certificates, retention, resource limits, or detection semantics.'
---

Start by recording the component revision, relevant configuration names, time range, structured refusal code, and last known successful boundary. Keep private keys, session tokens, and sensitive raw observations out of shared reports.

| Symptom                                                 | Guide                                                    |
| ------------------------------------------------------- | -------------------------------------------------------- |
| Agent fails to start or reload configuration            | [Agent foundation](/docs/troubleshooting/agent)          |
| Agent cannot enroll or certificate fails                | [Enrollment and TLS](/docs/troubleshooting/certificates) |
| Accepted events do not appear                           | [Ingestion and storage](/docs/troubleshooting/ingestion) |
| Consumer lag keeps growing                              | [Lag and state recovery](/docs/troubleshooting/lag)      |
| Rules do not fire or incidents do not appear            | [Detection](/docs/troubleshooting/detection)             |
| Events or detections look duplicated                    | [Duplicates](/docs/troubleshooting/duplicates)           |
| API unavailable, forbidden, or session lost             | [API and migration](/docs/troubleshooting/api)           |
| Spool grows, collector missing, frontend cannot connect | [Unimplemented paths](/docs/troubleshooting/planned)     |

A successful TLS handshake, durable ACK, committed writer position, query result, detection, and alert are different milestones. Use [the event lifecycle](/docs/architecture/event-lifecycle) to decide which one stopped advancing.

Do not disable verification, retimestamp records, skip offsets, delete state, or widen security limits before understanding the cause. The existing [observability surfaces](/docs/observability/health) are designed to make those boundaries visible.
