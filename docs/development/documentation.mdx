## Run locally

From this repository:

```bash
docker compose up --build
```

Open `http://localhost:3000`. Source is mounted; dependencies live in a named container volume. A lockfile hash avoids reinstalling unchanged dependencies at each startup and triggers `npm ci` when the lock changes. Set `WATCH_POLL=true` only when native filesystem notifications fail on your Docker Desktop/WSL mount.

## Validate

```bash
docker compose run --rm docs npm run check
```

This checks types, lint/content structure, generated references, formatting, and the production build with strict broken-link validation. Browser tests run separately against a real static server. See [the docs environment](/docs/deployment/documentation) for exact production commands.

## Evidence maintenance

`sources/manifest.json` records source revisions and hashes. `sources/` contains only selected generation/reference inputs; it is not imported by product code. Regular builds need no sibling repository or online API. Run `npm run sources:check` in the main workspace to detect changed/added/deleted product files requiring review.

To refresh, run `npm run sources:refresh` from a workspace with the independently checked-out repositories. Review its diff, update affected authored guides and implementation statuses, then run `npm run references` and `npm run check`. The refresh tool copies only explicit source artifacts, never `.env`, private keys, local credentials, or dependency caches.

Generated configuration keeps source expressions for defaults/bounds. Generated HTTP routes expose registrations and guards; they are not an invented OpenAPI specification. Schema reference includes canonical message definitions. ADRs remain historical documents with amendment warnings. Update the source snapshots rather than editing generated output.

## Author pages

Use ordinary MDX, a clear title/description, stable headings, meaningful cross-links, and source evidence. Use `FeatureStatus` once where it clarifies a page's scope. Put one canonical explanation at the owning topic and link to it. Do not bury implemented and planned behavior in the same unqualified paragraph.

The sidebar is ordered by category metadata and page position, with generated references nested under Reference. Document layout remains predictable; the homepage is intentionally more designed.

## Draw diagrams

Diagrams are typed data in `src/diagrams/<section>.ts`, rendered into the static HTML at build time. `FlowDiagram` draws components and their connections on a grid; `SequenceDiagram` draws numbered messages between participants, with `alt` branches for outcomes. Import the definition at the top of the page and place the component where the diagram belongs:

```mdx
import { durableAdmission } from '@site/src/diagrams/architecture';

<SequenceDiagram diagram={durableAdmission} />
```

Mermaid is not used. It measured label text in the reader's browser and sized boxes from that measurement, which clipped labels and scattered nodes on Windows. These diagrams do no browser-side measurement: boxes have fixed sizes, and text wraps inside them like any other HTML.

- Node kinds are `process`, `topic` (Redpanda), `store`, and `actor` (anything outside Seagull). Set `planned: true` on unbuilt parts; they render dashed.
- Edge kinds are `data` (solid), `control` (dashed, control-plane publication), and `ack` (dotted, acknowledgements).
- Place nodes with `col` and `row`; `cols` and `rows` span cells, and half rows are allowed. Ports and elbows are chosen automatically. Adjust them with `exit`, `enter`, `exitCol`, `enterCol`, `exitAt`, `enterAt`, and `channel`.
- Keep labels short. Identifiers such as `security.events.raw` render in monospace and wrap at dots.

A misspelled node ID is a type error. The build fails when nodes overlap, an edge runs through a node, or two edges share a segment. Browser tests check that text stays inside its box even when it renders wider than on the machine that drew it. `validate-content` rejects Mermaid fences.

## Versioning

The current docs version is labeled `V2 · development`. Do not freeze snapshots for unshipped releases. When a real supported release needs immutable documentation, use Docusaurus versioning from this repository:

```bash
npx docusaurus docs:version 2.0
```

Review generated versioned content and update navigation/status as part of that release. Product evidence revisions and documentation release labels remain separate concepts.
