---
title: 'Deploy the documentation website'
description: 'Docker-first development and a standalone static production image behind any reverse proxy.'
---

The documentation is an independent static website. It needs no Seagull backend, database, broker, Redis, API credentials, or external search service.

## Development

```bash
docker compose up --build
```

Open `http://localhost:3000`. Use Docker Engine with BuildKit and the Compose plugin (Compose v2 or newer); Docker Desktop supplies both on supported desktop platforms. This environment was exercised on Linux. macOS, WSL2, and Docker Desktop should use native file notifications first; `WATCH_POLL=true docker compose up` is the documented fallback when editing changes are missed.

Container dependencies live in their own volume. To add a dependency, run the package command through `docker compose run --rm docs npm install ...`, review the lockfile, and rebuild the development image. Host `node_modules` never overlays container dependencies.

## Production

```bash
docker build -t seagull-wiki:local   --build-arg DOCS_URL=https://docs.example.com .
docker run --rm --name seagull-wiki-production   --read-only --tmpfs /tmp:rw,noexec,nosuid,size=32m   --cap-drop ALL --security-opt no-new-privileges   -p 127.0.0.1:8080:8080 seagull-wiki:local
```

Replace the example public origin before deployment. The build stage performs static generation. The runtime contains Nginx and static assets, runs as UID 101, and serves internal HTTP on 8080. `/healthz` supplies a lightweight health check. Logs go to stdout/stderr; only temporary Nginx state needs `/tmp`.

The loopback publishing shown above is suitable for local validation or a host reverse proxy. A containerized proxy should connect over its managed network instead. Terminate TLS at that infrastructure boundary; the docs image manages no certificates.

## Subpath deployments

```bash
docker build -t seagull-wiki:subpath   --build-arg DOCS_URL=https://example.com   --build-arg DOCS_BASE_URL=/wiki/ .
```

The static output and custom 404 are placed under the prefix, and framework links use the configured base URL. Forward the path unchanged to Nginx; do not strip the prefix. Documentation routes then include the site's docs route, for example `/wiki/docs/architecture/overview/`. The prefix must differ from that docs route base. Docusaurus skips base-URL prefixing for a link that already starts with the base URL, so a `/docs/` prefix would leave every `/docs/...` link pointing outside the deployment; the configuration fails the build for that value. Changing these public values requires rebuilding, because the site is static.

## Routing and caching

Nginx resolves generated files/directories and returns the real custom 404 with HTTP 404. There is no catch-all SPA fallback. Hashed assets receive a one-year cache lifetime; HTML and other mutable entry points revalidate. Text assets are precompressed at build time and served with `gzip_static`; no runtime compression worker is required.

## Maintenance

Tag images by version or commit using your deployment pipeline. Build arguments `VERSION` and `REVISION` populate OCI metadata. Keep base image digests and npm lockfile reviewed. `npm run check` and `npm run test:browser` are the primary docs gates; the repository README and validation report record the environment actually tested.
